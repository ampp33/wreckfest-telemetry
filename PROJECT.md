# wreckfest-telemetry

Reads live process memory from a running **Wreckfest** instance (Wine/Proton on Linux) to extract post-race results — player names, cars, engines, class ratings, lap times, track/variation — without any in-game API or mod support.

## What it does

Wreckfest doesn't expose race results via any API, so this project reads them directly out of the game process's memory via `/proc/{pid}/mem`, the same technique tools like Cheat Engine use on Windows. There are two layers:

1. **Discovery** — figuring out *where* in memory the data lives (pointer chains, struct offsets, sentinel values). Done ad hoc/interactively, offsets hardcoded once found. Lives in the sibling [`../wf-memory-tool`](../wf-memory-tool) repo, not this one.
2. **Extraction** — once offsets are known, reading them directly and formatting a clean result. This is the everyday, production path, and is this repo (`wreckfest-telemetry`).

This repo's tool started life as `scraper.py` in a shared sandbox repo (alongside the `../wf-memory-tool` discovery tooling below), then a later `scraper_simple.py` variant, before being copied out into this dedicated repo as `wreckfest_telemetry.py` — see State/Known Issues for that transition as it actually happened, warts and all; entries from before the split still refer to it by its old name(s) at the time.

## Files

- **[wreckfest_telemetry.py](wreckfest_telemetry.py)** — the production tool, and this repo's only script. Standalone, no LLM/MCP needed at runtime.
  Usage:
  ```
  python wreckfest_telemetry.py --pid 1234                # attach and poll until Ctrl+C
  python wreckfest_telemetry.py --pid 1234 --json         # also emit JSON after each printed table
  python wreckfest_telemetry.py --pid 1234 --watch-tuning # watch the pre-race Tune screen live, print each slider as it's set
  python wreckfest_telemetry.py --pid 1234 --log-file out.jsonl  # append each completed race (+ persisted tuning) as JSON lines (default: race_log.jsonl)
  python wreckfest_telemetry.py --pid 1234 --no-api       # don't POST results even if config.json is set up
  ```
  `--pid` is required (no auto-detect); see `--help` (or the README) for the full current flag list, including `--interval`/`--debug`/`--config`.
- **[../wf-memory-tool/memory_mcp_server.py](../wf-memory-tool/memory_mcp_server.py)** *(sibling repo, not in this one)* — MCP server exposing raw CheatEngine-style memory primitives (see below). Used interactively with Claude for *discovery* work — finding new offsets, or re-discovering them after a game update breaks the hardcoded chain.
- **[../wf-memory-tool/find_pointers.py](../wf-memory-tool/find_pointers.py)** *(sibling repo, not in this one)* — one-off script to reverse-engineer pointer chains: given a known target address, scans all memory for 8-byte-aligned pointers into that address range. Used during initial discovery, not needed at runtime.

## How it works

### Player results (wreckfest_telemetry.py)
- **Fast path**: a hardcoded pointer chain (`module_base + CHAIN_STATIC_OFFSET → race_manager_ptr`, `+ CHAIN_ARRAY_OFFSET → slot[0]`) locates a canonical 24-slot array of player-result structs directly, in milliseconds.
- **Fallback path**: if the chain is broken/unreadable (e.g. after a game update shifts offsets, or — observed repeatedly — after the game process itself restarts), falls back to scanning memory for a sentinel byte pattern (`65535, -1000000`) that marks each struct, then clusters hits that are exactly `SLOT_STRIDE` (0x110) bytes apart to find the real 24-slot array (discarding stray UI-mirror sentinel hits). Scans only anonymous/writable regions (`anon_writable_regions()`) rather than all readable memory — the struct is dynamically allocated and rewritten per-race, so it can only live in heap-style memory, never read-only code/rodata or a file-backed mapping. ~8x faster than scanning everything readable (measured: 18s → 2.1s on a ~2.8GB process), with identical results.
- Each struct yields total time, best lap, class rating, and a pointer to a separate player/car data block (name, car model, engine spec as null-terminated strings).
- Validation guards (`validate_entry`, `read_player`) reject implausible values (lap times outside 3s–60min, stray Wine low-memory pointers, time-delta-looking strings) to avoid false positives from the sentinel scan.
- **Local player detection**: resolves the engine's own `CLIENT` singleton via the hash registry, reads its first field (the local client's assigned car/slot id, clamped from `-1` to `0` by the engine's own accessor when no network client exists), and matches that slot index against the 24-slot array. `PlayerResult.is_local` / `race_to_dict()`'s `player`/`others` split (see below) are built on this. See State/Known Issues (2026-07-30) for the two earlier signals this replaced and why.
- The 24-slot array's address is a fixed-size preallocated table for the whole process lifetime (repopulated per-race, never reallocated) — once found, `cached_addrs` stays valid indefinitely; "no currently-valid players at these addresses" (normal mid-race/menu state) never forces a rescan on its own, only a genuine read failure does. See State/Known Issues for the perf bug this fixed.

### Track / variation detection
**Primary — `detect_track_and_variation_live()`**: as of 2026-07-31, resolves the *actual English display names* via a direct, deterministic structural field chain traced from the game's own internal derivation (see State/Known Issues, 2026-07-31, for the full derivation and how it was found). No scanning, no caching, no manual cataloguing needed at all, and no guessing — every field read is a fixed offset, not a memory-adjacency heuristic:
1. **Variation name**: `*( *(event_settings_obj + 0x8) + 0x18 )` — one hop directly off the already-resolved `event_settings` object.
2. **Track name**: the raw base codename (`event_settings_obj + 0xa0`) is hashed (`wf_hash()`) and looked up against a live registry array (`ENVIRONMENT_SYS_IDX_OFF` → a flat array of `{idx}` entries, each cross-checked by stored hash + `strcmp`) to find its "environment" object, then the same `+0x8 → +0x18` chain gives the display name.
3. **Fallback** (only reached if `event_settings` itself can't be resolved, e.g. very early in process startup): the raw `"<track>_<variation>"` codename string resolved via `KNOWN_CODENAMES` (explicit map) then `_split_track_variation` (snake-case match against `KNOWN_TRACKS`/`KNOWN_VARIATIONS`). An unrecognized codename surfaces honestly as `"Unknown track (codename: '...')"` rather than guessing.

**Fallback — legacy 3-phase heuristic** (only reached if the live object itself can't be resolved, e.g. process not fully initialized): vtable heap scan → active-race marker scan → level-path anchor scan → brute-force substring scan. Known to occasionally return a wrong-but-plausible answer on its own (this was the original bug) — see State/Known Issues for the full history.

### Car tuning (pre-race setup screen)
`read_tuning()` / `watch_tuning()` (`--watch-tuning`): the pre-race Tune screen (suspension/gear ratio/differential/brake balance, each a 5-position 0-4 slider) uses a completely separate mechanism from game-state singletons like `event_settings` — UI widget names are hashed with **FNV-1a** (`fnv1a()`), formatted into a synthetic name `"menu/element/<hash>"`, and *that* string is resolved through the same registry/bucket-walk system as everything else. The value itself lives on each slider's `_TRACK` child widget, as a normalized float at `object+0x320` (`current_index / 4`). Since the discrete presets aren't retained anywhere once the race actually starts (converted to underlying physics constants instead), tuning must be captured live, during setup — `--watch-tuning` polls continuously and prints each category the moment it's set. A tab not yet visited this menu session is omitted rather than guessed (its widget doesn't exist until first opened).

`DIFFERENTIAL` is the one category that never gets a `_TRACK`/`_BAR`/`_THUMB` entry in that registry at all (confirmed by manually walking its exact hash bucket — real, non-empty, but holding an unrelated entry). Its value instead comes from `_read_differential()`, which reads a separate shared array of four `0x50`-byte structs (one per `TUNE_CATEGORIES` entry) found live via a Cheat Engine-style value scan. Since nothing points to that array either, it's relocated each game session by structural signature (`_find_tune_array()`: magic `0x00090005` + a sequential per-struct id + all 4 values in `[0, TUNE_MAX_INDEX]` + exact chain length of 4), scoped to just the memory region containing the already-reliable `SUSPENSION_TRACK` pointer to avoid false positives elsewhere in memory. Found once per process and cached. See State/Known Issues for the full derivation.

### Combined capture (default polling mode)
The default polling loop (`--pid` is the only required flag) does both of the above *together* in one continuous process: as of the loadout-array work (see State/Known Issues, 2026-08-06), tuning is read from the live equipped-part loadout array first (`_read_loadout_tuning()`), falling back to the older slider-widget read (`_read_tuning_widgets()`) for any category the array doesn't have a record for yet; separately, once a race finishes, `read_tuning_from_save()` re-reads the local player's car's *persisted* tuning straight from `cars5.ccrs` and that's what actually gets attached to the logged `RaceResult` (`tuning` field) — see State/Known Issues, 2026-08-05 part 13, for why the save file, not the live read, is the one wired into the finished-race pipeline. The combined record is printed, always appended as one line to `--log-file` (default `race_log.jsonl`, JSON-lines — one race per line; there's no flag to disable this), and — if `config.json` is set up — POSTed to the configured API (see below). This is the intended everyday mode: start it before setting up a car, let it run through the race, and each logged/posted result already carries the tuning that produced it.

### API posting (optional)
`load_config()` reads `config.json` (copy from `config.json.example`; listed in `.gitignore` since it holds real credentials) for `{"api_key": ..., "supabase_url": ..., "supabase_anon_key": ...}` — the backend is a Supabase-hosted API (the [wreckfest-2-race-log](../wreckfest-2-race-log) project). A missing or incomplete config file silently disables this feature (prints "API posting: disabled" at startup) rather than treating it as an error — every other feature works identically with no config at all. When present, `post_race_result()` POSTs the same race payload (plus `api_key`) to `supabase_url`, authenticated via an `apikey: <supabase_anon_key>` header, using stdlib `urllib.request` (no extra dependency). Runs alongside the file log, not instead of it — the file log always happens; posting is gated by `--no-api` (and by whether `config.json` resolves at all). A network failure or non-2xx response is caught, printed, and skipped — never raises, never interrupts the polling loop.

## MCP server (`wf-memory`)

Lives in the sibling [`../wf-memory-tool`](../wf-memory-tool) repo, not this one. Registered project-wide there via [`../wf-memory-tool/.mcp.json`](../wf-memory-tool/.mcp.json), stdio transport, no external dependencies (hand-rolled JSON-RPC over stdin/stdout).

Tools exposed:
| Tool | Purpose |
|---|---|
| `list_processes` | Find the game's PID by name |
| `list_memory_regions` | List `/proc/{pid}/maps` regions (address ranges, perms, mapped file) |
| `read_address` | Read one or more typed values at a specific address |
| `scan_for_value` | CheatEngine-style: scan all memory for a value, store candidates in a session |
| `filter_scan_results` | Narrow a scan session down after changing the value in-game |
| `read_region_dump` | Dump a block of memory as an array of typed values (find neighboring fields) |
| `scan_for_string` | Search memory for ASCII/UTF-16LE strings (names, tracks, etc.) |
| `read_bytes` | Hexdump a region (inspect raw layout/strings) |

**When to use it**: only for discovery/reverse-engineering — i.e. when `wreckfest_telemetry.py`'s hardcoded offsets stop working after a game update, or when adding a new stat that isn't extracted yet. For routine "get me the post-race stats" use, just run `wreckfest_telemetry.py` (this repo) directly; it needs no LLM tokens at all.

**Permissions**: tool-level allowlist lives in [`../wf-memory-tool/.claude/settings.local.json`](../wf-memory-tool/.claude/settings.local.json) (sibling repo). Reading `/proc/{pid}/mem` also requires ptrace permission from the OS — if reads fail with `PermissionError`, see the Yama ptrace_scope note in Known Issues below.

- **2026-08-16 — capture point changed, on explicit user instruction, to THE RESULTS SCREEN: "I just want the results AT RESULTS TIME, whatever that is, players gone or not."** This supersedes the trade-off recorded in the entry below, which had settled for logging at the local player's own finish and accepted that other racers were captured mid-race.

  **The signal**: every real racer's status field carries a terminal marker (`0x40` "run complete" or `STATUS_DNF_BIT`) **and** nobody is still circulating. Grounded in captured live data -- at the results screen every racer had a terminal marker, while mid-race several sat at `0x00`.

  **Three finality signals have now been tried, each wrong in a different way**, worth recording so none of them gets reintroduced:
  1. `FINISHED_BIT` -- not a finish signal at all, just the lap counter's low bit. Odd-lap races never logged.
  2. `any(player has 0x40)` -- fires when the **leader** crosses the line. Confirmed live: seven slots carried `0x40` simultaneously while the race ran on, so this snapshots a field with the local player potentially laps from home.
  3. `local player's own run is over` -- correct for the local player's position, but still captures every *other* racer mid-race, so their rows (and the API `notes` roster built from them) are not final results.

  **`_STILL_RACING_COUNT` + `_count_still_racing()`, new.** The "is anyone still out there" question cannot be answered from the returned player list: a racer still circulating who hasn't completed a lap has neither a valid lap time (so `validate_entry` rejects them) nor a terminal status (so `_validate_any_slot_relaxed` rejects them too), making them invisible at exactly the moment they most need to block a premature verdict. So the count is taken from the **raw slot array** each poll, using the same occupancy proof as the relaxed validators (real name + plausible class rating) so empty seats can't hold the results screen off forever. `_race_is_final()` gained a `pid` parameter to read it.

  **Accepted consequence, explicitly chosen by the user**: a racer who leaves at the results screen is removed from the slot array and everyone below shifts up, so positions captured at results time can differ from the positions as they stood at the finish. The entry below documents this happening -- the local player was P4 at their finish and read P3 two minutes later after the leader departed. The user's instruction is to record whatever the results screen shows regardless. Quitters therefore cannot hold logging open, by design.

  **Test-harness drift, second occurrence**: the throwaway suite's `scrape()` hand-mirrors `scrape_players()` and had to be updated again (to call `_count_still_racing()` and thread a test pid) or it silently exercised the old behaviour -- two scenario tests reported `False` until it was fixed. This is the second time this exact drift has bitten in one session; the harness mirrors production logic by hand and will keep drifting until it either calls the real function or is retired.

- **2026-08-16, second online race — two more corrections, both from the same race. `0x40` is not unique (seven slots carried it at once) and means "this racer's run is complete", and POSITIONS RENUMBER when a player leaves, which makes logging EARLY correct and waiting actively wrong.**

  **1. `0x40` is not unique and is not "local".** The entry below already retired it as an identity source; this race also disproves the "exactly one slot carries it" claim that made it plausible in the first place. Mid-race, **seven** slots carried `0x40` simultaneously -- precisely the racers who had completed the race, while the rest were still circulating -- and by the results screen nearly the whole field had it. Current reading: it marks a **completed run**. In every offline race it had been sampled in, the local player was the only slot showing it at that moment, which is why it looked like an identity flag for four races straight.
    - **Consequence, fixed**: `_race_is_final()` was testing `any(p.status_is_local for p in players)`, so it fired the instant the *leader* finished. In a race where the local player is several laps from home, that logs a mid-race snapshot as a finished race. It is now scoped to the **local player's own** status (`0x40` or `STATUS_DNF_BIT`) -- "this player's own run is over", which is exactly what the check has always wanted, and consistent with the 2026-08-08 decision to scope finality to the local player rather than the whole field. Synthetic tests cover all three cases (leader done + local still racing -> not final; local finished -> final; local DNF while others race -> final).

  **2. The position byte is a LIVE running order that renumbers when a racer leaves the array -- so it is only trustworthy at the moment the local player's own result settles.** Confirmed live and user-confirmed: the tool logged the local player at **P4** while the race was still running, and the user's real result was **4th**. Reading the same memory a couple of minutes later, at the results screen, gave **P3** -- because `Airsoft1300` (who had been P1) left, and everyone below shifted up a place.
    - **This inverts the intuition** that waiting for the race to fully end would be safer. Logging when the local player's run completes captured the correct position; waiting for the results screen would have recorded the user one place too high. The current edge-triggered design is right, and should not be "improved" by adding a wait.
    - **Known limitation, not fixed**: the flip side is that other racers still circulating are captured mid-race, so their rows in that snapshot (and in the API `notes` roster) are not their final results. Improving this would mean finding a moment when everyone has finished but nobody has left yet, and the 2026-08-08 entry records that waiting on every racer is how races silently went unlogged in the first place. - **2026-08-16, real online multiplayer race — CORRECTS the entry below: `STATUS_LOCAL_BIT` (0x40) is NOT the local player. A 22-player public race disproved it in one go, and the identity change built on it has been REVERTED. The position byte and the DNF bit both survived the same race and came out exactly right.**

  **What happened.** A real online race (Northland Raceway, 22 racers, 11 DNFs) produced an immediate identity mismatch that the session guard caught:
  ```
  0x40slot=4  CLIENT=6 (raw=6)  *** 0x40 AND CLIENT DISAGREE ***
    P1   slot4  TiamaT   st=0x41   <- 0x40 sat HERE (the race winner)
    P12  slot6  Ampp33   st=0x17 DNF   <- the actual local player
  ```
  `CLIENT` was **correct** (slot 6). The bit that had been promoted above it was on someone else entirely. Because identity was resolving differently tick to tick, the fingerprint kept changing and the tool logged **four** separate bad entries (`TiamaT`, `envirovore`, `sagetherainwing`, `timmydangles`) before the process was killed. All four were removed from `race_log.jsonl` (backup in scratchpad). The `confirmed_local_name` guard did its job on every one of them -- flagged the mismatch and skipped the API post -- so nothing wrong was published.

  **Why the earlier evidence was misleading, and the lesson.** 0x40 matched the local player in a solo hot lap, an offline AI race, and two offline 24-car races -- four races, three "modes", zero disagreements, cross-checked against CLIENT every tick. That looked like strong verification and it was not, because **all of it was offline, where the local player is the only human present**. Any "human" / "host" / "owning client" flag is indistinguishable from "local player" under that condition. The variable that mattered was never tested until a populated online lobby existed. Best current guess for the bit is host/session-owner; unconfirmed and no longer relied upon for identity.
  - Worth noting the earlier entry explicitly flagged "no live race has yet seated the local player at a non-zero slot" as the outstanding gap -- the risk was correctly identified, but the change shipped ahead of closing it. Verification across several instances of the *same* condition is not verification across conditions.

  **Reverted**: `_mark_local_player()` no longer consults 0x40 at all; `CLIENT` is the identity source again, with its existing fallbacks unchanged. The constant's docstring now documents the bit as meaning-unknown and explicitly not identity. The synthetic test that asserted "the bit must beat CLIENT" was inverted to encode the real online scenario instead (0x40 on another player, CLIENT correct -> CLIENT wins), plus a case proving the bit can't hijack identity even when CLIENT is unresolvable.

  **Still used, honestly scoped**: 0x40 remains the `_race_is_final()` edge, purely because it has empirically appeared at the moment results finalize in all five races observed (4 offline, 1 online) -- a timing property that holds regardless of whose slot it lands on. That rests on observation, not understanding, and should be replaced when a better finality signal turns up.

  **What this race CONFIRMED (against real human opponents, not AI):**
  - **The position byte is exactly right.** The user reported finishing **12th, DNF'd**; the byte gave `P12`, and the full field came out unique across 1..22. First validation of it online.
  - **`STATUS_DNF_BIT` is right.** The local player carried `0x17` (DNF bit set) and had genuinely DNF'd; 11 DNFs flagged.
  - **A new wrinkle to watch**: several genuine finishers carried `st=0x00` (P2 `ccdirt`, P3 `envirovore`) rather than the `0x01`/`0x04` seen offline. So the status field is NOT reliably populated for every racer online. It doesn't affect current logic -- those players pass `validate_entry()` on lap time alone and never reach `_validate_any_slot_relaxed()` -- but any future check that assumes "status populated == real racer" would be wrong online.

- **2026-08-15, end of night — SOLVED, completely: the game's OWN finishing position is byte 0 of the `OFF_FINISHED_FLAG` word. This retires every ranking heuristic in the project and closes the DNF sub-ordering problem that had been open since the lap counter was found. Verified exact against a full 24-car race's real results screen.**

  **What it is.** `OFF_FINISHED_FLAG` (`addr-32`) is read as an int32 and the project has always used byte 1 of it as the lap counter (`OFF_LAP_COUNTER`, `addr-31`). **Byte 0 of that same word is the finishing position, zero-indexed** (`position = (flag & 0xFF) + 1`). It was sitting one byte away from a field this project has been reading all along, unexamined.

  **How it was found** -- worth recording, because the method is the reusable part: rather than keep guessing at sort keys, the user was asked to read the **real in-game finishing order straight off the results screen** (they were still sitting on it), and every field in and around the slot struct (`-256..+512`) *and* the player struct behind `player_ptr` was then swept for one that reproduces that exact sequence, scoring candidates by how many adjacent pairs they order correctly. Two things scored 12/14 -- `total_time_ms` descending (and its two copies at `+96`/`+100`), and the flag word ascending. The flag word's *low byte* then turned out to be an exact, duplicate-free 0..23.

  **Verification, against two independent ground truths**: the local player's byte read `1` for a user-confirmed **2nd place**, and the 15-strong DNF block matched the results screen **name for name, in order**. Running the real `scrape_players()` afterwards reproduced all 24 positions exactly.

  **This also explains why no `total_time_ms` direction could ever work**, and retires that whole line of investigation. The user confirmed the engine ranks DNFs by **order of death, first out placed last**. Elapsed time only tracks progress while a car is still moving: in the everyone-DNF race the local player was on track longest (91s) and placed *last*, having been immobilised, whereas in a normal race the longest-surviving DNFs genuinely did place highest. Ascending fits one race, descending fits the other, and neither is right -- which is exactly the contradiction the 2026-08-15 entries below kept running into. The position byte sidesteps it entirely by not inferring anything.

  **Implementation**: new `OFF_FINISH_POSITION`, `PlayerResult.finish_position`, and `_rank_players()`, which is now what both `scrape_players()` paths sort with. It uses the engine's byte **only when the set looks coherent** -- every player non-zero and no duplicates -- and otherwise falls back to the previous `_position_sort_key()` heuristic unchanged. That guard matters: a partially-populated or duplicated set (mid-race, stale slots, a mode that doesn't fill it) would otherwise produce a confidently wrong order, which is worse than an approximate one that is honest about being approximate. Both paths are covered by synthetic tests -- one asserting a deliberately heuristic-defying position set is respected, one asserting duplicates fall back.

- **2026-08-15, end of session — SHIPPED: the status bitfield is now wired in as the primary mechanism for BOTH local-player identity and race finality, replacing CLIENT-as-primary and the bogus parity bit respectively. Verified live end-to-end: a race that previously could never log now logs correctly.**

  **What changed** (`wreckfest_telemetry.py`):
  1. **New constants + field**: `OFF_STATUS_FLAGS = -36`, `STATUS_LOCAL_BIT = 0x40`, `STATUS_DNF_BIT = 0x10`; `PlayerResult.status_flags` populated in both `read_player()` and `_read_player_native_only()` (one extra `ri32`, no extra pass), with `.dnf` and `.status_is_local` properties.
  2. **`_mark_local_player()` now resolves identity from `STATUS_LOCAL_BIT` first**, falling back to `CLIENT` only when the bit isn't populated (i.e. mid-race). The scan walks the **raw slot addresses**, not `pairs` -- deliberately, because the entire bug being fixed is that the local player can be absent from `pairs`; scanning `pairs` would miss precisely the case that matters. All the existing salvage tiers still run underneath, so a 0-lap local player is still recovered.
  3. **`_race_is_final()` no longer rests on `FINISHED_BIT`.** It returns True once `STATUS_LOCAL_BIT` is present on any slot -- verified live to appear exactly when the local player's result settles (it flipped `0->65` at the instant they crossed the line in one race, and appeared as results populated in another where *nobody finished*). The old parity check survives only as a fallback for a hypothetical mode that never populates the status field, and is now **hardened with a completed-lap requirement**, which independently blocks the bogus mid-race log caught earlier this session.
  4. **`_position_sort_key()` sorts on the real DNF flag first** (`(p.dnf, -p.laps_completed, p.total_time_ms)`). - **2026-07-28 — BUG RESOLVED: found and fixed a serious continuous-scan performance bug in the main polling loop; also added local-player identification.**
  - **User asked how long a scrape takes**, since the whole point of the default polling mode is to run in the background and react quickly once a race finishes. Measured directly: `scan_for_sentinels()` (the fallback path — the fast pointer chain has been stale since the 2026-07-27 entry above) takes **~35 seconds** to scan this process's ~2.7GB of readable memory (~77MB/s via `/proc/pid/mem`, almost entirely syscall/`sys` time, not CPU — confirmed via `time`: `sys 0m32s` vs `user 0m2.5s`). Slower than this doc's earlier "a few seconds" claim, which was apparently never measured precisely.
  - **Found something much worse while investigating**: `main()`'s loop set `scan_needed = True` unconditionally both right after printing a new race's results (to "pick up the next race cleanly") and whenever results were momentarily absent (`players` falsy). Since `scrape_players()`'s cached-path falls through to a full rescan whenever the cached addresses don't currently produce *valid* players — which is the **normal, expected state for the entire duration of a race, and in menus** (the results screen data literally doesn't exist yet) — this meant the loop was doing a full ~35s scan on every single poll tick, back-to-back with no rest, for the entire time the user wasn't sitting on the results screen. In practice: after the initial scan, the tool could spend effectively 100% of its time re-scanning rather than politely waiting at `--interval`, and detecting a finished race could be delayed by up to another full scan cycle past when it actually finished.
  - **Root cause**: `scrape_players()`/`main()` conflated two different things under one `None`/falsy signal — "the 24-slot array's location is wrong/stale" (should trigger a rescan) vs. "this array's location is still correct, it just doesn't currently hold finished-race data" (normal, should never trigger a rescan). The array is a fixed-size preallocated table for the process's entire lifetime (same premise the pre-existing `cached_addrs` caching was already built on) — there was never a good reason to discard a known-good location just because the current tick has no results.
  - **Fix**: `scrape_players()` now returns `(None, cached_addrs)` — preserving the known-good addresses — when the cached location is read successfully but produces zero currently-valid players, and only returns `(None, None)` on a genuine hard read failure (`FileNotFoundError`/`PermissionError`, i.e. the process is actually gone). `main()`'s loop now checks the returned `cached_addrs` (not just `players`) to decide whether a rescan is actually needed, and no longer force-discards it after printing a race or when results clear.
  - **Live-verified the fix**: full 24-slot location discovery still costs the same one-time ~35s (unavoidable given the underlying `/proc/pid/mem` throughput, and the stale fast-path chain — re-discovering that chain remains the only way to eliminate this scan entirely, still not done), but every steady-state tick afterward — tested with 20 consecutive calls against the live game — now takes **~0.28ms**, down from a continuous ~35s stall per tick. This is the actual fix for "run in the background, detect a finished race fast": the expensive step now happens once per game session instead of on every single tick whenever a race isn't currently showing results.
